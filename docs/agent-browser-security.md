# 操作エンジンの安全設計

## 結論

`browser-agent`は、`agent-browser`を低レベルの操作エンジンとして利用します。ただし、上流CLIをそのまま公開しません。サイト、認証、実行設定、許可操作、トップレベルオリジン、出力、実行状態を外側のレイヤーで制限します。

撮影は別経路です。Playwright Libraryで宣言済みの準備操作とマスクを適用し、完成PNGだけを公開します。

## 実行の流れ

```text
呼び出し元
  │
  ├─ browser ─ 外側allowlist ─ 強制設定 ─ agent-browser ─ Chrome
  │                 │              │
  │                 │              └─ 固定実行ファイル、private profile、隔離download
  │                 └─ 操作前後の全タブ検査、内容を含まない監査
  │
  └─ capture ─ 撮影定義 ─ Playwright Library ─ mask ─ 検査済みPNG
```

## 信頼するもの

- リポジトリでレビューしたサイト定義、撮影定義、操作方針
- `package-lock.json`で固定した依存関係
- 承認済みSHA-256と一致する`agent-browser`ネイティブバイナリ
- 固定したシステム配置から解決し、現在ユーザーが置き換えられないChrome実行ファイル
- Playwrightが解決したChromium実行ファイル
- データ正本を所有する現在ユーザー

ページ内容、ページ由来のselector、外部環境変数、グローバルCLI、proxy設定は安全設定の入力として信頼しません。

## 起動時に強制する状態

1. ネイティブバイナリの版とSHA-256、default-deny方針の内容を検証する。
2. 継承した`AGENT_BROWSER_*`と標準proxy環境変数を削除する。
3. 回収に必要なセッション記録を先に作る。
4. privateな設定、profile、download隔離領域を作る。
5. `about:blank`で起動する。
6. streamを無効化し、無効状態を確認する。
7. viewport、device scale factor、locale、headerを設定する。
8. state方式では、認証stateを一度だけ読み込む。
9. Chromeが管理profileに生成した起動マーカーとdaemon PIDを記録する。
10. 明示された許可オリジンへ移動する。

ブラウザ起動前に失敗した場合は、作成済みの一時データを取り消します。起動後に安全な終了を確認できない場合は、セッション記録を残します。`unlock`はこの記録を使って回収可否を判断します。

## 操作の二重制限

外側では、引数を構造として解析してから許可済みコマンドへ変換します。raw引数の透過は行いません。内側では、上流のaction名と一致するdefault-deny方針を使います。

方針ファイルは[agent-browser-action-policy.json](../config/agent-browser-action-policy.json)です。操作エンジンを呼び出すたびに、default-denyと許可action集合が実装上の承認集合に完全一致することを確認します。`doctor`とテストでも同じ検査を行います。

`screenshot`や`pdf`を拒否する理由は、撮影レイヤーのマスク検査を迂回するためです。HTML、入力値、属性、Cookie、storage、任意JavaScriptを拒否する理由は、ページ内容や認証情報を必要以上に取り出せるためです。

## オリジン境界

操作の前後に全タブを列挙し、各トップレベルURLを`allowedOrigins`と照合します。popupやリンク操作で許可外オリジンが開いた場合も検知し、セッション全体を終了します。未知のtarget、複数のactive tab、無効なURLも拒否します。

この検査はトップレベル境界です。サブリソース、WebSocket、WebRTC、DNSを含む通信全体の封じ込めではありません。認証profileやstate replayと上流のnetwork allowlistを安全に併用できないため、ネットワーク境界を装っていません。

## 認証データの所有権

profile方式では、`login open`だけが正本profileを直接開きます。通常操作と撮影は正本をprivateな作業用profileへコピーし、正本へ書き戻しません。

state方式では、ログイン用の一時profileから明示的な`login save`で認証stateを作ります。既存stateを直接上書きせず、サイズ、JSON構造、Playwright contextへの読込可否を検査してから原子的に置き換えます。通常操作は作業用profileへstateを一度だけ読み込み、自動保存やrestoreを行いません。

## 異常終了と解除

セッションごとに短時間のコマンドmutexを置き、同時操作を拒否します。内部セッション名は、サイト、利用者指定名、用途を区切った値からハッシュで生成します。単純な文字列連結による衝突を防ぎます。

profile正本を読む処理にはサイト単位のロックを置きます。監査記録の更新もサイト単位で直列化し、異なるセッションの完了が重なっても記録を失いません。ロックファイルは、内容を書き終えてから原子的に公開します。

異常終了後の`unlock`は、全対象について次を検査してから一括で退避します。

- 記録したowner PIDが停止している
- agent-browserの該当セッションがない
- Chromeが記録済みuser-data-dirを使用していない
- `lsof`または`fuser`でopen holderがない

1件でも稼働中または検査不能なら、ロックやメタデータを変更しません。停止済みと確認できたファイルだけをprivate archiveへ移します。

## 記録しない情報

監査記録には、selector、入力文字列、URLのパスやクエリ、ページ本文、snapshot、コマンド出力、エラー本文を保存しません。保存するのは、操作名、成否、オリジン、非内容系エラーコードだけです。

download先はセッション専用の隔離領域です。外へ取り出すコマンドは提供せず、正常終了または安全な古い実行状態の回収時に削除します。

## 検証範囲

自動統合テストは、使い捨てのローカルHTTPサイトと一時profileだけを使います。実在サービスの認証状態は使いません。

実在サービスでのカナリア確認は別工程です。対象サイト、実行する読み取り操作、終了条件をユーザーが承認した後に、1サイトずつ実行します。
